# 统一随手记、理账与持续分类

日期：2026-09-09
状态：首个本地闭环已实现，完整设计仍分阶段推进。实际能力与未完成项见 [验收记录](../../qa/2026-09-09-unified-capture.md)。

## 1. 已确认的产品原则

- 统一输入入口支持文字、语音、图片、原始手写笔画，输入时不要求选类型。可混合记录消费、当天复盘、自媒体灵感、以后想做的事。
- 原始记录先保存，点“整理”才提取；日常输入不能因为 AI 不可用而丢失。
- 提取结果遵守各功能的读写格式和领域校验，通过已有功能的保存/查询/展示路径使用，不能另建一套“AI 任务”页面或对象。
- 初步不明确或无法分类的内容进入统一 Others 收纳中心。
- 持续分类包括细分、合并、新建分类和重新整理历史内容。账单分类可以自动提出建议，但必须经人工确认后生效；该要求高于助手可选的免确认设置。
- 保留原文和媒体，可追溯、微调、撤销；重复整理不能重复创建账单、日记或任务。

## 1.1 三部分职责与依赖

这是用户确认的结构原则；后续实现必须以此分层，不能由 AI 输出决定页面或存储结构。

| 部分 | 固定对接方式 | 职责边界 |
| --- | --- | --- |
| UI | 从领域查询接口取得类型化读取模型；通过领域命令提交用户操作 | 渲染、输入、确认和微调。不能解析模型原始 JSON、按 provider 分叉卡片或直接修改存储。手动和 AI 创建的相同数据走同一组件。 |
| 数据 | 标准 schema、领域命令、查询模型、版本和迁移规则 | 定义有效数据、解析验证、引用完整性、确认状态、幂等、保存和撤销。只有此层能把候选结果变为正式事实。读取模型可按页面投影，但含义以标准领域对象为准。 |
| AI 整理 | 接收来源及 schema 的可写部分，输出符合提案契约的候选数据 | 提取/归类/建议，只填写允许字段；不能发明领域字段、改变 schema、提供 UI 布局或直接落库。更换模型不改变 UI 和领域格式。 |

数据流：原始输入保存 → AI 候选提案 → 数据层解析/领域校验 → 必要的人工确认 → 领域命令提交 → 统一查询投影 → UI 展示。人工输入可以跳过 AI，但不能跳过数据层。

schema 契约只维护一个权威定义：领域 schema 派生可写提案字段和模型输出约束，UI 读取类型及校验样例需通过一致性检查。模型提示词不另外手写一套互相漂移的字段规范；供应商不支持结构化输出时，仍按同一契约在本地校验。

AI 的输出 schema 是标准数据 schema 的可写子集，不要求模型填充由应用生成的稳定 ID、版本、确认人和回执。此分工避免把“格式相同”误实现为“信任 AI 填入全部持久字段”。

结构兼容、领域有效、语义正确分开验收：金额能解析不代表识别金额正确；分类 ID 存在不代表类别合适。来源证据、人工分类确认和修正 Trace 保留。

## 1.2 固定骨架与动态内容

- 稳定核心字段表达业务事实：身份、版本、类型、金额/币种、时间、正文、来源及状态。动态分类通过 categoryID/parentID/合并映射改变数据，不改变账单或任务 schema。
- 文本、图片、手写、音频通过固定 blocks/Asset 引用扩展内容数量和顺序；追加当天回想使用受控追加命令，不通过新增临时 JSON 字段绕过已有正文。
- 可选扩展使用固定结构 `attributes[] = {fieldID, value}`。value 为有类型的联合：`text | decimal | boolean | date | enumID | recordRef`，不接收任意深层 JSON、脚本或布局指令。
- FieldDefinition 是配置数据：稳定 fieldID、名称、所属 kind、valueType、枚举候选、是否多值。实例属性必须引用已经启用的定义，并通过类型/范围/目标引用校验。首版由应用提供定义，不因此新增面向用户的复杂字段编辑器。
- AI 只能填充本次提供的 fieldID；无法表达的新信息先保留在原文/Others，可提出扩展建议，不能自行启用字段。扩展定义的增改是单独受控操作，不混在普通提取中执行。
- 扩展字段不得覆盖或替代核心字段：例如 attributes 中的价格不能替代账单 amount，标签不能绕过正式分类确认，日期属性不能偷偷创建排期。
- UI 按已知核心字段固定展示；已知扩展可用统一的类型化详情行读取，不为每个 AI 新值创建页面。新提案中的未知字段拒绝并保留原文；读取历史/同步数据中无法解释的扩展保留原始值但不参与计算或动作，显示需要兼容支持。
- schemaVersion（结构）、record revision（对象内容）、taxonomyRevision（分类）及 fieldDefinitionsRevision（扩展定义）分别记录。新增分类、合并分类或填写已定义属性不递增结构版本。
- “框架不变”指常规内容扩展不改核心结构；真正改变字段类型/语义时必须发布新结构版本和显式迁移。遇到不支持的未来版本不能静默重写为旧版并丢字段。
- attributes 是预留的受控扩展位置；仍优先使用明确的领域类型，不把所有功能退化成通用键值数据库。

## 2. 页面与职责

建议新增“随手记”作为统一编辑入口；助手继续负责对话和主动请求，助手也可对随手记发起整理。

- 随手记：时间顺序显示原始记录；编辑器支持文字块、图片、手写画布、录音及转写。一键整理；显示各内容的去向、待确认/待补充/失败状态。
- 理账：金额与描述的轻量输入、账单明细、按币种和分类查看；复用相同提取和保存契约。
- Others：一个统一入口，区分“无法识别用途”“账单待确认分类”“缺少账单字段”等原因，不把所有内容混成无法筛选的杂物堆。
- 任务/回想/灵感：读取各自标准对象，通过来源入口回到原记录。同一原始记录可以产生多类内容。
- 分类建议：显示新增/细分/合并前后、受影响记录及账单金额；支持修改建议、确认部分或全部、拒绝。

底部导航的最终布局独立做视觉确认；先完成数据契约和最小业务闭环，不在本稿中推定删除现有主页面。

## 3. 共同格式与解析边界

以下类型为拟新增的 Swift Codable 契约，不表示当前已存在。借用 typed-service-contracts 的输入/结果/错误分层原则，复用当前 Swift 工程的错误处理和领域引擎，不引入 TypeScript/Zod。

### 3.1 原始输入 CaptureEntry

- `id`：本地生成的稳定 ID；`revision`：单调增加的修订号。
- `recordedAt`：真实保存时间；`timeZoneIdentifier`：输入时区。
- `blocks`：有序判别联合 `text | image | handwriting | audio`；每块有稳定 `blockID`。
- 文本块保存原文；媒体块引用本地 Asset，不把 Base64 塞进日记、任务备注或用量日志。
- Asset 保存稳定 ID、媒体类型、内容哈希、文件长度与本地文件引用。手写保存可继续编辑的笔画；缩略图/OCR 为派生数据。语音保留原录音及独立转写版本。
- 修改输入产生新 revision；已有整理结果仍指向原 revision，不能偷偷切换来源。

### 3.2 AI 输出 ExtractionProposal

- 必填：`schemaVersion`、`captureID`、`sourceRevision`、`items`。
- 每个 item：本次提案唯一 `candidateID`、`kind`、`evidence[]`、该 kind 专用 payload。
- `kind` 仅允许 `ledger | recall | inspiration | futureIdea | task | other`，禁止模型创建未知种类。
- evidence 引用存在的 blockID。模型提供精确原文 quote，由应用核对后解析并保存对应版本 Unicode scalar 起止偏移；图片/笔画引用 Asset ID，OCR 引用其转写版本；没有证据的金额、日期和执行动作不能自动落库。
- `task` payload 复用现有 V2ScheduleOperation 允许的字段。其他 payload 见下一节。
- 模型不能决定 durable ID、保存路径、完成状态、确认人或写入成功；这些由应用生成。
- 解析顺序：JSON 解码 → 字段/类型校验 → 来源/版本校验 → 领域规则校验 → 生成可执行命令 → 保存 → 通过正式查询读取结果。
- 不合法对象保留为失败候选，原始内容仍在收纳中心；不把坏数据作为另一种“可显示的 AI JSON”偷偷保存。

## 4. 各功能格式规则

| 功能 | 拟定必填与关键字段 | 领域约束与现有页面接入 |
| --- | --- | --- |
| 账单 LedgerEntry | 稳定 ID、`direction`、`amount`、`currency`、`description`、`recordedAt`、来源；可选 `occurredLocalDate`/`occurredAt`、商家 | 金额用十进制字符串解码为 Decimal，不用浮点数；支出/收入和金额正负分开，转账不作为消费。货币使用受支持的三字母代码。币种缺失只能采用已配置默认值并标记依据，未配置则待补充。不得把记录时间伪装成消费时间。 |
| 回想 RecallAppend | `localDate`、时区、`text`、来源；可选真实任务/排期/执行引用 | 现有 V2RecallEntry 是当天一条记录，包含 text、hasHandwriting 和引用数组。AI 通过新增追加命令合并片段，保留已有正文、真实引用、手写标记；不能直接用 saveRecallEntry 覆盖。 |
| 灵感 InspirationEntry | 稳定 ID、`title`、`body`、记录时间、来源；可选分类 ID | 保留细节和改口。当前无独立灵感模型，需要新建正式模型、保存命令和读视图，不能冒充现有日志能力。 |
| 以后想做 FutureIdea | 稳定 ID、`text`、来源、可选期望日期 | “想试试”“也许以后”属于意向，不自动创建必须执行的日程；可明确转换为任务。与灵感共享记录基础字段，以 kind 区分。 |
| 任务 Task | 现有 V2ScheduleProposal/Operation、任务/排期稳定 ID、来源 | 仅明确要执行的事项进入既有日程引擎。保留数量、时间、否定和备注，不编造日期。已有任务引用不明先追问。日期、排期与任务本体保持现有区分。 |
| Others | 来源、原始片段或媒体引用、`reasonCode`、候选建议 | 即使不能生成任何领域对象，也必须可见、可搜索、可再次整理；缺金额的账单候选不计入账单总额。 |

账单字段的依据分别记录 `explicit | configuredDefault | unresolved`。金额、币种或收支方向未解决的对象只能作为待补充候选，不能混入正式总额。只是不知道分类而其他字段已确定的账单可以保存，但正式 categoryID 为保留类别 `others`，AI 分类在建议中等待确认。不同币种首版分开统计，不自动换汇。

“理财想法”不是已发生交易；单纯提到商品价格也不是消费事实。只能从原文提取已发生、明确记账的记录。

## 5. 统一保存与 UI 不变量

- 手动表单、语音、AI、导入都调用相同领域命令；来源仅作追踪信息，不参与决定任务卡片结构。
- 相同任务状态/选中状态/排期，在今天页面使用同一投影和组件。助手修改只用已有短暂高亮，不改变圆角、布局、交互或创建第二份任务。
- 回想新增 `appendExtractedRecall` 类命令，在同一个 snapshot 提交中读取当前正文、追加新片段、合并引用。记录追加来源 ID，重复请求幂等。
- 每个结果有 `proposed | needsConfirmation | needsInformation | applied | rejected | failed | undone` 状态；混合内容允许账单待确认而复盘已保存，界面必须逐项说明，不能笼统显示“全部完成”。
- 一组互相依赖的任务操作保持原子提交；跨功能整理使用父批次及分项回执，不承诺跨媒体文件和数据库的虚假全局原子性。
- 幂等键由应用管理：原记录 ID、revision、整理批次和持久候选映射。断线重试复用批次；重新分析先对照既有来源绑定显示变更，不作为全新内容盲目追加。
- 用户已编辑/确认的结果不会被重新分析覆盖；更新必须展示差异。撤销检查对象版本，保留后续人工修改，冲突时说明具体对象。
- 同一真实消费出现在多张图片/文本中，来源 ID 幂等不足以去重。提供疑似重复提示；不凭相近金额时间静默合并两笔真实消费。

## 6. 动态分类及人工确认

分类身份和名称分离：稳定 `categoryID`、所属领域 `domain`、名称、可选 `parentID`、状态 `active | merged`、可选 `mergedIntoID`。分类名称变化不改变历史对象身份。

- 首次账单分类：AI 提出建议；确认前留在账单 Others。可在整理结果中一键确认多笔，也可逐笔修改。金额/描述输入不因分类未确认而丢失。
- 细分：展示父类、新子类以及每条记录将移至哪类；不能仅按类别名批量猜测消费用途。
- 合并：用户选保留类别或设置新名称，预览源类、目标类、受影响记录和各币种金额。确认后原子更新引用；旧类别保留合并映射以便历史来源、搜索与同步识别。
- 未使用分类也可以合并，记录数为 0 时明确显示；没有必要先建立账单才能整理分类。
- 历史账单重新归类：始终需要新的人工确认。手动分类不会因 AI 新建议被静默覆盖。
- 分类建议允许接受部分、修改、拒绝；部分接受只影响所选记录，拒绝记录在相同内容/分类版本下不反复弹出。
- 系统保留 `others`，不可删除、合并消失或形成父子环；用户可把其中记录移到已确认类别。账单类别与任务类别不可跨领域合并。
- 任务/灵感首版也以建议预览后确认方式调整分类；不把改分类等同于修改任务父子结构或排期。
- 合并/拆分回执保存变更前后及引用版本；撤销能恢复分类归属，若后续已编辑则先报告冲突，不覆盖。
- 动态建议由用户点“重新整理”或新增内容后发现需要细分时产生；首版不在每次打开页面时全库重分类。

## 7. Trace 与问题复盘

Trace 横跨三部分，不能成为第四套业务数据来源。应用在接收记录/整理操作时生成 root traceID，每阶段有 spanID/parentSpanID，关联相同来源修订、候选、目标对象和回执。

- 阶段覆盖原始输入保存、模型提取、结构校验、领域校验、等待确认、实际提交、读取投影与首次结果展示；记录真实起止和结果，确认等待时长与模型耗时分开。
- UI 只在分项结果首次呈现或展示失败时记录呈现事件，不随每次 SwiftUI 重绘重复采集。已提交回执是写入成功的依据，不能把模型成功响应或屏幕显示当作保存成功。
- schema、分类、字段定义、提示词与模型版本关联到同一批次，便于区分识别错误、契约错误、保存错误和展示错误。
- 复盘使用原始来源版本、历史提案和回执比较；调试重放默认只生成候选和差异，不再次执行写入或人工确认过的分类迁移。


### 用量事件：扩展现有 V2UsageTrace

保留当前默认不存自由文本、可关闭、30 天/2000 条上限。新增提取开始/结束、校验失败、分项保存、分类建议/确认/拒绝/合并、人工修正、重复拦截、撤销事件。

每个事件关联 `captureID`、`sourceRevision`、`batchID`、`candidateID`、`receiptID`（适用者），以及真实 provider/model、schema/prompt/分类版本、各阶段耗时、错误码、重试次数、实际调用次数；不记录 Key、原始媒体、隐藏思维或服务商原始敏感错误。

### 可查看的整理历史

业务数据保存原始记录、提案版本、字段证据、实际对象链接及变更回执。用户可从某条账单查看“原文 → AI 提取 → 校验 → 人工修正 → 当前结果”。这些是恢复与撤销需要的业务记录，不因关闭用量 Trace 而禁用基本撤销。

导出调试事件默认只有脱敏元数据；用户另行选择包含哪些原始内容及整理差异，不把个人日记/账单默认上传到代码仓库。观察指标包括金额/日期修正比例、分类接受/改选/拒绝率、Others 转出率、重复创建拦截、各阶段时延；不能仅用“JSON 成功解析”作为识别正确率。

固定错误码：`invalidSchema`、`missingEvidence`、`invalidAmount`、`unknownCurrency`、`missingRequiredField`、`invalidReference`、`staleSource`、`staleTarget`、`duplicateCandidate`、`assetUnavailable`、`providerFailure`、`persistenceFailure`。界面转为具体可处理的说明，保留原始输入和重试位置。

## 8. 多模态与同步边界

- 文字/转写先接通统一契约；图片/OCR/手写识别后续走相同候选提案接口，不绕过验证器直接写账单。
- 原始笔画与识别文本分开保存。当前手写是按天保存的 PKDrawing 文件，需新增按来源的媒体存储，不能让新的手写覆盖当天画布。
- 媒体先成功保存并校验哈希，再提交记录引用；中断保留草稿，不发布指向缺失文件的已完成记录。
- 识别所需图片/录音只发送给当前配置且支持该能力的服务。不能假定现有文本模型支持视觉；不支持时原样保存并明确显示待识别。
- 现有 schedule.md 同步仅涵盖其原有任务协议。本功能须另加版本化 capture/ledger/category 文档及资产清单后才可同步；首个闭环先本地保存，不把新内容静默塞入旧协议或声称已完成多设备同步。

## 9. 分阶段实施与验收

1. 按 UI / 数据 / AI 三部分建立共同来源、版本、提案/回执格式；每类输入输出样本与校验器。先完成文字/语音混合记录 → Others、账单、回想、灵感/意向、任务的最小闭环。
2. 理账读取页、分类确认、手动分类、动态细分/合并、历史改类及撤销；建立真实人工修正 Trace。
3. 图片/笔画/录音资产持久化与识别；重启恢复和来源定位；最后扩展版本化同步协议。

必须具备的验收案例：

- 同一标准领域样本经手动/AI 入口后可由相同查询接口读取，UI 不依赖模型响应格式或服务商；未知提案字段被拦截。
- 新建/细分/合并分类和填写已定义扩展属性不改变 schemaVersion；未知扩展读取保全、核心字段不可被扩展覆盖、不支持版本不可静默降级。
- 同一 traceID 能定位 AI、数据校验/写入及 UI 呈现阶段；重放只比较结果，不重复产生业务副作用。

- 同一句混合输入分别生成四类结果，每项有原始证据和目标读取验证；疑问/想法不自动变成消费或执行任务。
- 格式错误、未知 ID、金额缺失、币种未知、无证据日期、旧版本响应均不能污染正式数据。
- 同一天已有文字及手写，AI 追加回想后旧内容和笔画保留；重复整理/重试/重启不重复追加。
- 初步分类不确定和等待确认的账单出现在 Others；没有人工确认时类别和分类统计不改变。
- 创建/细分/合并含零记录类别、迁移历史记录、拒绝建议、部分确认、撤销及并发冲突；每币种账单总额在仅分类操作前后保持不变。
- 手动、语音和 AI 生成同等任务，在相同状态的今天/任务视图截图及操作一致。不能用“来源不同”解释 UI 差异。
- 手写可编辑、图片可读、录音可播放，重启后引用有效；模型不支持视觉时能保存原始内容且不伪造结果。
- Trace 可定位慢在识别/模型/校验/保存哪一段，以及人工修改发生在哪个字段；关闭采集和导出脱敏有效。

### 9.1 2026-09-12 C 批次：专用记账入口与人工校正

C 批次把随手记中的“理账”入口显示为“记账”，与现有独立账本页保持同一标题，不增加新的底部 Tab 或账本数据存储。记一笔首先是一段自然语言草稿，可通过共用多行输入和语音控件完成；金额、币种、收支、日期和分类只在整理预览或用户选择手动补充时出现。语音完成后回填同一草稿，用户可以修改原文再整理。

专用记账整理只保存 `CaptureEntry`、`CaptureBatch` 和候选提案，不因全局免确认设置而自动写入账单或其他混合内容。每个候选逐项显示待核对、待补充、待确认分类、已保存、已拒绝、失败和已撤销状态；账单分类在人工确认前继续使用 `others`，拒绝建议也保留未分类账单。无法确认金额、币种或收支的原文保留在候选/收纳中心，不能把记录时间当作消费日期，也不能把混合任务、灵感或价格讨论自动变成账单。

候选确认前可通过强类型 `V2LedgerCandidateDraft` 修订账单字段。`core.capture.reviseCandidate` 和 `core.capture.confirmLedgerCandidate` 都要求 `batchID`、`candidateID` 与 `sourceRevision`，在同一来源版本下执行；前者把最新字段保存为候选 ID 绑定的 typed override，原始 `proposal` 保持不变，并为每项字段变更记录带候选 ID 的 `V2CaptureCorrection`。后者在一次跨 `core.capture`/`core.ledger` 提交中读取当前 draft、保存修订并创建账单行，避免“先保存修正再用旧候选确认”。缺字段的候选可以补充后重试，已产生目标对象的回执拒绝再次覆盖。重复确认返回原回执，保存失败保留原文和待处理状态。完成账单保存后仍沿用现有分类确认与撤销命令，人工分类不会被 AI 建议静默覆盖。

草稿与混合随手记分开，关闭输入页会停止整理但保留本次原话；保存后“再记一笔”清空当前草稿和来源指针，以新来源开始，旧原文和回执仍保留。原话修改后须重新整理，不能继续提交旧核对结果；不同批次的核对卡片使用独立编辑状态。整理失败在当前页显示并允许重试，不以父页面弹窗打断输入。

本批不扩展已入账账单的编辑系统；手动入口在随手记或助手/插件停用时仍可通过现有账单命令独立保存到 `others`。真实模型调用、图片/音频识别和跨设备同步继续按本稿后续阶段单独验收。

本稿包含目标架构与后续验收要求；实际交付范围以 2026-09-09 验收记录为准。尚未实现的注册扩展字段、全库 AI 批量分类与新协议同步不会因本稿描述而视为完成。
