# 本地优先、多渠道备份与后续付费同步

日期：2026-09-14。

状态：用户已确认产品方向；下述实现设计是本轮落地方案，新增全量备份代码尚未实施。现有 GitHub 日程同步保持原范围，不计作全量备份完成。

## 用户已确认的范围

1. 数据首先保存在本地，离线可用，不依赖账号或订阅才能编辑。
2. 支持多渠道备份的产品方向；当前只开发 GitHub。
3. 预留 WebDAV 与 NAS，后续按需要接入，当前不开发空实现或假连接入口。
4. 调研 Obsidian 的 E2EE、冲突处理、版本恢复、选择性同步及运行限制，作为后续收费服务的依据。

## 现有能力与缺口

| 能力 | 本地证据 | 当前边界 |
| --- | --- | --- |
| 本地业务保存 | `V2JSONSnapshotStore` / `V2AppSnapshot`，schema 2，原子写入，schema 1 迁移前备份 | 迁移副本不等于持续版本备份 |
| 日程 GitHub 同步 | `V2GitHubScheduleClient`、`V2ScheduleGitHubView`、`V2ScheduleAutomaticSync` | 同步 Markdown 日程，不包含完整财务、附件、助手会话与记忆 |
| 日程合并/恢复 | `V2ScheduleMerge`、`V2ScheduleDocumentState`、冲突处理 | 已有日程规则继续使用；不自动适用于其他领域 |
| 附件与其他存储 | `V2CaptureAssetStore`、`V2MemoryJSONStore`、助手 workspace/`V2AssistantArchive` | 独立存储，需要一致快照与引用校验 |
| 全量 GitHub 备份、WebDAV/NAS、托管 E2EE | 尚无实现 | 不能显示成已连接或已同步 |

上述名称均对应当前项目类型或文件。日程同步的真实远端/手机验收状态仍按 `docs/roadmap.md` 原记录管理。

## 备份与同步分工

- **本地保存：** 每次编辑先成功写本地，再调度任何网络操作；网络失败不撤销用户编辑。
- **备份：** 给某个时刻的资料建立可校验、可恢复的独立版本，允许多目的地保存同一版本。用户明确选择版本后恢复。
- **同步：** 多台设备对同一资料库持续读写，需要共同基线、稳定 ID、删除记录、冲突和迁移协议。全量快照不能通过“取最新文件”冒充多设备同步。
- 现有 `schedule.md` 可继续独立同步。全量备份另用目录/分支，不能触发日程 AI 工作流。

## GitHub 首期交付范围

### 1. 统一、版本化备份包

备份包至少记录 `formatVersion`、`backupID`、`datasetID`、源设备随机 ID、创建时间、各领域 schema、包含/排除范围、文件路径、长度及 SHA-256 清单。标识不使用邮箱、手机名称等私人信息。领域 JSON 与附件按引用导出，时间格式和字节编码固定并提供恢复样本。

包含任务、排期、执行证据、回想、记账/财务、笔记、已选择的助手会话及记忆；附件原件随其引用纳入。先完成全量一致快照，再开放可选范围。若必需附件缺失或不支持某个领域，应显示不完整原因，禁止标记为“完整备份”。

凭据、Keychain、设备书签、临时导出文件、网络调试日志、缓存和正在执行的任务句柄不进入备份。业务回执保留必要的幂等/审计信息；恢复后不自动重放 outbox。不能递归打包整个 Application Support 目录作为替代。

读取通过协调的快照边界完成，防止业务数据和附件分别取自不同的时刻。若期间产生写入，保持本次冻结版本并在之后产生下一次备份；不阻塞用户持续输入。

### 2. 本地恢复闭环先于远端上传

本地生成不可变备份版本，完整落盘后才记录成功。恢复先在独立暂存目录做格式、哈希、引用与 schema 检查，任何未知版本、损坏或缺附件均不触碰现有数据。恢复前建立当前资料的保护副本，暂停相关写作业，在可回滚的事务边界切换全部存储。

恢复界面先给出日期、范围和数量摘要，不要求用户处理内部字段。首期全库恢复明确告知替换范围，完成后重新建立本设备同步绑定；不继承另一设备的同步凭据、文件授权或排队副作用。启动时识别未完成恢复并回到最后一个完整版本。

### 3. GitHub 适配

- 使用用户指定的私有数据仓库。代码仓库与备份数据分开；先读取仓库属性和权限确认目的地，不自动创建仓库，不沿用日程凭据扩大数据范围。
- 仅要求目标仓库 Contents 权限；凭据留在 Keychain，不需要 Workflow 写权限。授权失败显示可操作原因，不输出令牌或正文。
- 初期手动“立即备份”；成功前读取校验结果，显示备份时间和范围。失败保留同一备份 ID 供重试，重复点击不得生成内容相同的多份远端版本。
- 每个备份使用唯一路径/版本。上传文件后最后提交完整清单；清单未提交的中断备份不出现在可恢复列表。并发提交以远端版本校验控制，禁止 force push 或覆盖他人的快照。
- 先复用现有 HTTP transport 与凭据存储方式。现有日程客户端限制 Markdown 与 1 MB，不能直接拿它存全量包或只是放宽后缀；新增备份适配器保持职责清楚。
- 首期方案采用 Git 数据对象、tree、commit 与非强制 ref 更新实现多文件发布，分块与内存上限必须在实施测试中固定。GitHub 不是无限附件仓库：超限应保留本地并说明失败，不静默跳过附件。容量/请求配额限制以[GitHub 官方文档](https://docs.github.com/en/rest/repos/contents)为依据，不能混淆现有客户端的 1 MB 限制与 GitHub 的整体限制。
- 首次连接展示真实数据范围及“私有仓库仍不等于端到端加密”；财务、聊天或音频等范围须在应用里明确授权。开发与远端验收先使用合成数据，本次方向确认不代表授权上传全部现有私人资料。

### 4. 多渠道扩展接口

业务层只生成、校验和恢复一种备份包。渠道层负责枚举完整版本、发布、下载；返回渠道能力（大小限制、条件提交支持）与可读失败状态。GitHub adapter 是当前唯一实现，不建通用插件引擎。

后续 WebDAV 可使用条件请求/ETag 与最后写入完成标记；NAS 优先经其 WebDAV 服务复用适配器。只有实际需求要求 SMB、SFTP 或厂商 API 时才增加另一实现。渠道不参与业务合并，也不决定计费。

增加渠道后可把同一 backupID 扇出到多个目的地，分别记录成功/失败；其中一个失败不影响本地和已成功副本，也不让一个远端的删除传播到所有备份。

## 后续收费同步方向（研发候选，不在首期开发）

产品研究见[Obsidian 官方机制与收费分析](../../sync/2026-09-14-obsidian-sync-research.md)。

| 专题 | 本项目决策 / 建议 | 发布门槛 |
| --- | --- | --- |
| E2EE | 托管同步默认开启；格式可独立于存储渠道。正文、附件、必要身份关联绑定校验；最少元数据 | 跨端测试向量、丢钥恢复、密钥轮换、设备撤销、篡改/回滚检测与独立审查 |
| 业务冲突 | 共同基线与对象版本；财务不能最后写入覆盖，保留双方并人工确认 | 两设备离线/乱序/重复/删除冲突；总金额和付款事实不被篡改 |
| 高级恢复 | 付费延长历史、增加容量和批量恢复；基础恢复始终可用 | 中断恢复、全库回滚、旧 schema、缺附件、幂等副作用均验证 |
| 选择性同步 | 按领域、附件类型和设备选择；范围缺失不视为删除 | 未下载对象不被回写清空；首次上传前排除；远端删除独立确认 |
| 运行限制 | 前台可靠同步与重试优先，后台尽力；常开客户端另行开发 | 真机弱网、休眠、杀进程、超额、过期与重新连接验证 |
| 收费 | 本地与自有存储保留；托管便利性、空间、历史和运维作为收入来源 | 成本核算、恢复演练、退款/到期/导出政策完成后定价，当前不接支付 |

E2EE 同步不会自动提供云端 AI 明文读取能力。需要云端处理时由用户明确选择发送范围；Android 与 Web 是独立客户端工程，统一格式只是兼容前提，不能称为已经跨端可用。

## 实施顺序与验收

1. **G1 本地备份格式与恢复：** 格式金样、数据/附件往返、缺失与篡改拒绝、恢复中断不损坏本地、恢复不重放付款/通知/同步。
2. **G2 GitHub 备份渠道：** 合成数据上传、列表、下载、恢复；401/403/404/409/限流/弱网中断及并发重试；清单完整才可恢复。以真实私有测试仓库端到端结果收尾。
3. **G3 App 接入：** 在功能与插件/数据管理位置提供“备份与恢复”，默认展示本地状态；连接一次后“立即备份”只需一次点击。复用应用主题，真实点按验证配置、保存、取消、重试、恢复预览/取消、失败与禁用状态。
4. **G4 发布前验收：** 真机重启与恢复，跨设备下载同一备份，统计数量与哈希一致；检查权限范围与导出中无凭据；用户明确范围后才接真实个人数据。
5. **S1 收费同步研究验证：** 独立实现 E2EE 和全领域同步原型，评估成本与收费策略；WebDAV/NAS 待 GitHub 闭环稳定后排期。

完成标准是“能够从远端完整恢复”，不是“API 返回上传成功”。以上 G1–G4 均未在本轮实现或验收；本轮完成决策记录、现状审计、官方调研与路线拆分。
